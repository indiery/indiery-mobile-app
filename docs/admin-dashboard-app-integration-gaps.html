Admin Dashboard
App Integration Gaps

An honest gap assessment against every section of the “Detailed Admin Panel” specification.

Assessment date: 16 October 2026
Scope: admin website, backend API/database, customer app and partner app
Purpose: show what is partial, configuration-only or not yet integrated—without demo data or inflated completion claims.

Executive summary

The core operational path is connected: real orders, drivers, customers, KYC, vehicle pricing, payouts, coins, cancellations, push delivery, reports and basic B2B operations. However, the full 21-section specification is not yet completely integrated.

Most important gaps: service-area enforcement, runtime settings enforcement, real multi-admin authorization, full support/in-app notification integration, advanced refund processing, complete audit coverage, document-expiry data, advanced analytics, and full B2B contract/invoice/payment workflows.

Status definitions

  • CONNECTED works through app/backend/database and is covered in the completed-feature guide.
  • PARTIAL some functionality exists, but important requirements or app-side effects remain.
  • NOT INTEGRATED visible configuration or requested workflow does not yet control the customer/partner apps or backend runtime.

Detailed app-side gaps

Customer app

  • No service-zone/operating-hours response that disables booking and explains why.
  • No maintenance-mode banner or booking lock controlled by admin settings.
  • No support-ticket inbox, ticket creation, attachments or threaded responses.
  • No in-app announcement feed/read-state.
  • No explicit admin-configured wallet-floor rule synchronized from settings.
  • No B2B-authorized contact experience; B2B dispatch remains admin-led.

Partner app

  • No re-KYC interval or document-expiry reminders driven by admin-configured dates.
  • No service-zone/vehicle availability policy driven by admin records.
  • No admin support-ticket conversation or escalation UI.
  • No in-app announcement feed.
  • No configurable pickup search radius or assignment policy consumed from the settings module.

Backend platform

  • No single validated runtime-settings service with versioning and cache invalidation.
  • No real RBAC matrix; current admin middleware authorizes the admin role broadly.
  • No centralized immutable audit-event model capturing actor, request, before/after and outcome.
  • No support, announcement, service-area, invoice, refund-request or business-document domain models.
  • No scheduled job layer for document expiry, campaigns, invoice due dates or re-KYC.

Recommended delivery plan

Phase 1 — runtime controls and authorization

  • Create validated system-settings and service-area schemas.
  • Enforce maintenance, coverage, hours, wallet floor and search radius in backend APIs.
  • Add mobile app banners/errors for each enforced condition.
  • Implement real admin identities, invitations, deactivation and role/city permissions.
  • Add centralized audit events to every privileged mutation.

Phase 2 — financial and support workflows

  • Build gateway-backed refund requests with idempotent provider calls.
  • Build support tickets, attachments, threads, SLA and customer/partner app screens.
  • Build in-app announcements with targeting and read state.
  • Add document expiry dates, reminder jobs and re-KYC lifecycle.

Phase 3 — B2B and advanced intelligence

  • Expand business profiles, verification, contracts and authorized contacts.
  • Add persistent invoices, due dates, receipts, credits and reconciliation.
  • Add advanced report APIs, pagination and Excel exports.
  • Add assignment distance/performance ranking and delay monitoring.

Production-completion checklist

A feature should be marked fully integrated only when all relevant checks below are satisfied:

  • Backend has a validated model and authorized API.
  • Admin action changes persistent application state.
  • Customer and/or partner app consumes the state where required.
  • The user receives a clear result or error.
  • The action is auditable with actor, time and outcome.
  • Empty/error/loading states are implemented.
  • Tests cover authorization, validation and failure recovery.
  • No placeholder records, invented totals or misleading provider status exist.
Current conclusion: core operations are usable and connected, while the gaps listed in this report must be completed before the entire original admin-panel document can accurately be declared fully integrated.
